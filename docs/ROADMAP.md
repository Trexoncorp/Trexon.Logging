# Предложение по реализации

Это план для обсуждения, а не утверждённый контракт API.
Текущий этап ограничен подготовкой NuGet-пакета и CI/CD.

## Принцип

Взять из Loguru удобство: один вызов для записи, готовый консольный вывод,
простое подключение файлов и контекста. Внутри использовать отдельный
экземпляр логгера с явным временем жизни; статический фасад должен быть
удобным входом в этот экземпляр, не единственным способом работы.

Пример желаемого использования, пока не реализован:

```csharp
Log.Info("Application started");
Log.AddFile("logs/app.log");
Log.Info("Order {OrderId} created", orderId);
```

Уровень проверяется до разбора шаблона и форматирования. Сохраняются исходный
шаблон, именованные свойства и Exception, чтобы текстовый и JSON-вывод могли
использовать одно событие. Интерполяция `$"..."` не заменяет структурные шаблоны.

## Этапы

| Этап | Состав | Условие готовности |
| --- | --- | --- |
| 1. Контракт и минимальный логгер | LogLevel, LogEvent, экземпляр Logger, фасад Log, console sink, минимальный уровень | После установки достаточно одного вызова; проверены уровни, шаблоны, Exception и отключённый вывод |
| 2. Настройка и контекст | Add/Remove, параметры sink, Bind, AsyncLocal scope, фильтры, текстовый и JSON-формат | Разные sinks имеют независимые настройки; контекст не протекает между параллельными запросами |
| 3. Файлы | File sink, ротация по размеру/времени, retention, затем compression | Данные корректны при конкурентной записи и ротации; ошибки диска обрабатываются предсказуемо |
| 4. Очередь и жизненный цикл | Ограниченный Channel, политика переполнения, FlushAsync, DisposeAsync | Проверены порядок, блокировки/потери согласно политике, ошибка sink и завершение с очередью |
| 5. Интеграция с .NET | Отдельный пакет Trexon.Logging.Extensions.Logging, ILoggerProvider, scopes, DI, Host, конфигурация | Логи приложения и ASP.NET Core идут через один pipeline; нет дублирования и циклов |
| 6. Укрепление перед 1.0 | Документация, примеры, нагрузочные проверки, benchmarks, стабилизация API | Проверены Linux/Windows/macOS, реальные сценарии потребления NuGet, правила совместимости API |

## Границы первой версии

Начать с одного пакета `Trexon.Logging`, без внешних зависимостей. Console и File
включить в основной пакет ради простого старта. Зависимости от Microsoft
Extensions вынести в адаптер, когда дойдём до интеграции.

С первого этапа определить поведение при ошибке sink и владение ресурсами.
Синхронный logger должен поддерживать корректное завершение; очередь добавится
на четвёртом этапе. Файловая запись в несколько процессов требует отдельного
решения и не считается автоматически поддержанной из-за thread safety.

Не начинать с сетевых sinks, произвольных пользовательских уровней и
автоматического перехвата всех исключений. Сначала проверить, что API удобен
на небольшом консольном приложении и простом сервисе.
